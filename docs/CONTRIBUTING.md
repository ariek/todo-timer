# 開発ルール

個人開発だが、履歴を追いやすくするために以下のルールで運用する。

## ディレクトリ

| ディレクトリ | 役割 |
| --- | --- |
| `public/` | 公開する本体。GitHub Actions がここだけを GitHub Pages に配信する |
| `docs/` | 仕様書、このルール、デザイン案 |
| `dev/` | 確認用サーバー、コミット前チェック、絵の一覧 |
| `.github/` | PR の雛形と Pages 公開のワークフロー |

## 作業の流れ

1. `main` から作業ブランチを切って実装する。この時点ではコミットしない。
2. ローカルで確認する。Mac のブラウザは `http://127.0.0.1:8765/public/`、iPhone は同じ Wi-Fi から `http://<MacのIP>:8765/public/`（サーバーは下記コマンドで起動）。全画面の見え方は、その URL をホーム画面に追加して確認する。
3. コミット前に `./dev/check.sh` を実行し、JS の構文と CSS の波括弧の対応を確認する（CSS は途中で壊れると、それ以降の指定が全部無効になる）。
4. 確認して OK になってからコミットし、プッシュして PR を作る。直しがあれば同じブランチで続け、再確認してからコミットする。
5. PR を Squash and merge で取り込み、必要ならタグを打つ。

ローカル確認用のサーバー（プロジェクトのフォルダで実行）:

```bash
/usr/bin/python3 dev/server.py
```

このサーバーはキャッシュを禁止するヘッダーを付けるので、ファイルを変えたらアプリを閉じて開き直すだけで反映される。

ローカル確認の URL は HTTPS ではないため、サービスワーカー（オフライン動作と「更新する」の帯）は動かない。それらは公開版で確認する。

## ブランチ

| ブランチ | 役割 |
| --- | --- |
| `main` | 公開ブランチ。GitHub Pages はここを配信する。常に動く状態を保つ。 |
| 作業ブランチ | 1つの変更ごとに `main` から切る。完了したら `main` に取り込んで削除する。 |

### 作業ブランチの命名

`種別/短い説明` の形式。説明は英小文字とハイフン。

| 種別 | 用途 | 例 |
| --- | --- | --- |
| `feat` | 機能追加 | `feat/task-form` |
| `fix` | 不具合修正 | `fix/streak-reset` |
| `style` | 見た目やSVGの変更 | `style/room-cards` |
| `docs` | 仕様書やREADMEの変更 | `docs/spec-timer` |
| `chore` | 設定や整理など | `chore/gitignore` |

### 取り込み方

- GitHub 上で Pull Request を作り、**Squash and merge** で取り込む。作業中の細かいコミットは1つにまとまり、`main` の履歴は1機能1コミットになる。
- PR のタイトルはそのまま `main` のコミットメッセージになるので、下記のコミットメッセージ形式で書く。
- 取り込み後は作業ブランチを削除する（GitHub の自動削除を有効にする）。
- `main` への直接プッシュは、誤字修正のような一行の変更に限る。

## コミットメッセージ

[Conventional Commits](https://www.conventionalcommits.org/ja/) をベースにする。本文は日本語でよい。

```
種別: 変更内容の要約

（任意）なぜ変更したかの説明
```

- 種別はブランチと同じ `feat` / `fix` / `style` / `docs` / `chore` に加え、`refactor`（動作を変えない整理）を使う。
- 要約は 50 文字以内。「〜を追加」「〜を修正」のように、何をしたかが分かる形にする。文末に句点は付けない。
- 1コミットには1つの論理的な変更だけを入れる。「フォーム追加と誤字修正」のような混在は分ける。
- 本文には「何を」より「なぜ」を書く。仕様書の変更を伴う場合はその旨を書く。

例:

```
feat: やること追加フォームを実装

難易度と繰り返しを選べるようにした。期限は次のPRで対応する。
```

```
fix: 日付が変わった直後にストリークが0になる問題を修正
```

## リリース時の注意

- アプリのファイル（`public/` 以下）を変更して `main` に取り込むときは、`public/sw.js` の `CACHE_VERSION` と `public/app.js` の `APP_VERSION` を同じ値に上げる。これが変わらないと、インストール済みの端末に更新通知が出ない。
- アイコンを変えるときは `public/icons/icon.svg` を直し、PNG は次のコマンドで作り直す（macOS）。

```bash
cd public/icons && qlmanage -t -s 1024 -o . icon.svg && python3 -c "from PIL import Image; s=Image.open('icon.svg.png').convert('RGBA'); [s.resize((n,n), Image.LANCZOS).save(f) for f,n in [('icon-512.png',512),('icon-192.png',192)]]; bg=Image.new('RGBA',(180,180),'#fbf6ee'); bg.alpha_composite(s.resize((180,180), Image.LANCZOS)); bg.convert('RGB').save('apple-touch-icon.png')" && rm icon.svg.png
```

## バージョン

- 番号は `v メジャー.マイナー.パッチ` の3桁。`feat`（機能追加）でマイナーを、`fix` / `style` / `refactor` / `chore`（修正、見た目の調整、動作を変えない整理）でパッチを上げる。
- アプリのファイルを変える PR では、`public/app.js` の `APP_VERSION` と `public/sw.js` の `CACHE_VERSION` を同じ番号に上げる。
- その PR を `main` に取り込んだら、同じ番号のタグを打ってプッシュする（例: `v0.2.3`）。ドキュメントだけの変更ではタグを打たない。
- 最初の遊べる版は `v0.1.0`。

### バージョンを上げる前の確認

番号を上げる PR では、コードの変更に加えて次を確認する。多くは `grep` と読み直しで済む。動かして確かめるものは、その PR で触った範囲に絞る。

毎回見る:

- **不自然な日本語になっていないか**: 画面の文言（見出し、ボタン、トースト、確認ダイアログ、空のときの案内、読み上げ用のラベル）を、その PR で触った画面を中心に読み直す。内部名（`categories` など）や「N日」のようなプログラム的な表現が画面に出ていないか、言葉の対応（`docs/SPEC.md` 0章）とずれていないかを見る。
- **不要な機能が残っていないか**: 仕様を変えたときに、古い仕組み（使わなくなった関数・CSS・要素・仕様書の記述・`dev/check.sh` の関数名）が残っていないかを見る。`grep` で古い名前を探し、残っていれば同じ PR で消す。
- **仕様書との一致**: 変えた動きが `docs/SPEC.md` の該当章に反映され、決定事項に日付付きで残っているか。古い記述が残っていないか。
- **サービスワーカーの更新**: `APP_VERSION` と `CACHE_VERSION` が同じ番号か。新しく足したファイルが `sw.js` の取り込み一覧に入っているか（入っていないとオフラインで壊れる）。
- **`dev/check.sh` の関数一覧**: 関数を足したり消したりしたら一覧も直す。

該当する変更をしたときだけ見る:

- **古いデータで起動できるか（0.x の間）**: データの項目を足したとき、その項目がないデータを読み込んでも初期値で埋まって動くことを確認する。変換処理は持たない方針なので、読み込み時の初期値で吸収する。
- **作業中（タイマーが動いている状態）で壊れないか**: やること画面やセッションまわりを触ったとき。作業中に画面の切り替え、再読み込み、やめる、まとめを閉じる、を行っても状態がおかしくならないか。
- **空の状態の表示**: 一覧やカードの表示を触ったとき。クエスト0件、やること0件、記録なし、次回待ちだけ、の各画面。
- **iPhone 固有の動き**: ドラッグ、日付などの入力欄、固定表示の覆い、全画面の上下余白を触ったとき。Mac のブラウザと挙動が違うので実機で見る。
- **PC 幅の表示**: レイアウトを触ったとき。900px までの中央寄せで崩れていないか。

## PR の書き方

本文は次の3つの見出しで書く。`.github/PULL_REQUEST_TEMPLATE.md` に雛形がある。

- **概要** … 何を変えたか。箇条書き
- **確認したこと** … どの環境で何を確かめたか
- **未確認** … 確かめられていないこと（実機でのみ分かることなど）

## 仕様変更

- 仕様を変えるときは `docs/SPEC.md` を先に直し、同じ PR にコードの変更を入れる。
- 決めたことは `docs/SPEC.md` 末尾の「決定事項の記録」に日付付きで追記する。
